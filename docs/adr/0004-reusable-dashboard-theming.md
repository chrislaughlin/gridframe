# Reusable Dashboard theming with consumer-owned controls

Gridframe exposes Dashboard theming as a reusable capability rather than implementing it only in the example web app. Theme selection and Theme Builder controls remain consumer-owned experiences—the bundled web app demonstrates them without forcing those controls or their product decisions on every Gridframe integration. The web app applies its selected Theme across the full app chrome and Dashboard, while consumers can scope a Theme to an individual Dashboard. On a first visit the web app derives Light or Dark from the operating-system preference; once a user explicitly selects a Theme, that app-wide preference is retained across visits. The High Contrast Theme preset uses a near-black foundation, near-white text, strongly separated surfaces, vivid cyan interaction color, and a yellow focus indicator. Ordinary text and controls target WCAG AAA contrast, and Visualizations must not communicate distinctions through color alone.

The web app resolves the effective Theme before first paint so the initial page does not flash the wrong Theme, then hydrates from the same state. Unavailable or corrupt browser storage falls back safely to the current operating-system-derived Light or Dark preset. Operating-system forced-colors mode takes precedence over the selected Theme; Gridframe preserves semantic structure, labels, borders, and focus behavior while allowing system colors to control presentation.

The reusable capability is data-first and color-only in its first version: typography, spacing, shadows, and geometry remain outside the Theme contract. It exposes typed Theme and Theme foundation objects, the three Theme presets, generation and validation functions, and JSON and CSS-variable serializers. These pure APIs live in a server-safe `@gridframe/react/theme` subpath because Themes describe the React presentation system rather than Gridframe’s framework-neutral core. Generation and validation return structured issues rather than throwing. A `GridframeThemeScope` wrapper and the `PanelDashboard` Theme convenience prop remain in the main `@gridframe/react` entry; neither path requires a global React provider. If a rendering API receives a malformed Theme, it keeps the inherited Theme and emits a clear development warning; production fails safely without logging user color values.

The Theme Builder uses guided generation: a user chooses background, surface, text, primary, accent, and destructive values as the Theme foundation. Gridframe derives the remaining semantic colors, borders, focus color, and chart series, while the Theme Builder exposes the result and its contrast checks without requiring users to author every Theme value. Preview accepts any valid colors and never silently alters them, but activation is blocked until essential text, controls, focus indicators, and chart distinctions meet WCAG AA; the builder explains failures and suggests passing replacements. Draft colors are scoped to a representative preview canvas so an invalid draft cannot make the Theme Builder itself unreadable; saving and using a valid Custom theme applies it app-wide.

The web app retains one valid Custom theme in browser storage and lets the user preview, save and use, or reset it. A Custom theme has a short user-facing name that defaults to “Custom”; the stable switcher category remains “Custom” and shows the chosen name as supporting text. The Theme foundation draft is autosaved separately so unfinished or inaccessible work survives navigation and browser restarts, but only the last valid saved Custom theme appears in the switcher. Resetting the draft restores the saved Custom theme’s foundation, or the Light foundation when no Custom theme exists. Deleting a Custom theme requires confirmation and removes its saved value and draft; if it was active, the app falls back to the current operating-system-derived Light or Dark preset. Theme selection, Custom theme saves, and deletion synchronize across open tabs through browser storage events, while each tab’s in-progress draft remains isolated. A saved Custom theme can be copied as typed JSON for the reusable Gridframe API or as CSS variables for direct integration.

The Theme Builder accepts six-digit hex colors through visual pickers and editable text fields. The reusable theming API accepts validated CSS color strings, while generated and exported Themes are normalized to OKLCH so derivation and contrast calculations remain predictable.

Exported Theme JSON uses a versioned envelope containing its version, name, Theme foundation, and generated Theme values. Import is outside the initial scope, but the version boundary allows future import and migration without reinterpreting unversioned artifacts.

The web app exposes Theme selection in its persistent header, offering Light, Dark, High Contrast, and Custom once one has been saved. The equivalent control is available in the mobile menu, and both link to the dedicated Theme Builder at `/themes`.

The Theme Builder preview uses static data and covers a representative Dashboard Card, form controls, buttons, links, loading/success/error states, a table, and every Visualization family. It also exposes hover, focus, and selected states plus the contrast report, without relying on Dashboard APIs or saved user data.
